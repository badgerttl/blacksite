# Open WebUI hardening profile

This project applies a security-first local profile based on Open WebUI's official hardening guide. Settings that would disable required Blacksite functionality or require deployment-specific infrastructure are deliberately deferred rather than applied blindly.

## Applied defaults

- Bind published services to `127.0.0.1` and restrict Open WebUI CORS to its two local browser origins.
- Use an explicit persistent `WEBUI_SECRET_KEY` generated by `./blacksite init`.
- Disable signup, assign any future account the `pending` role, enforce password validation, and expire JWTs after 24 hours.
- Disable follow-up generation and reconcile the setting through Open WebUI's task configuration API.
- Enable API-key endpoint restrictions while preserving chat/model APIs and Blacksite's tool/configuration reconciler.
- Disable community sharing, administrator bulk chat export, administrator access to other users' chats, direct model connections, and OpenAI API passthrough.
- Keep regular-user workspace creation/import permissions disabled. Tools remain enabled because they are a core Blacksite feature.
- Disable automatic `pip` installation from Tool/Function frontmatter.
- Enable metadata-only audit logging to a rotated file and stdout; use structured JSON application logs.
- Keep outbound TLS verification enabled, local/private RAG web fetch disabled, and outbound redirect following disabled.
- Disable forwarding externally hosted profile images.
- Apply `X-Frame-Options`, `X-Content-Type-Options`, referrer, and browser permissions headers. CSP is report-only until browser workflows have been validated.
- Apply a restrictive CSP to rendered artifact iframes that blocks outbound connections.
- Limit uploads to 50 MB and 10 files per request, with extensions needed for documents and security-tool evidence.
- Drop all Linux capabilities and enable `no-new-privileges` for Open WebUI and its one-shot tool deployer.
- Pin the official Open WebUI image to a release rather than `main` or `latest`.

Persistent ConfigVar settings are reconciled by `scripts/deploy-openwebui-tools.py`, because Open WebUI's database values take precedence over environment defaults after first startup.

## Deferred because they require deployment decisions

- **HTTPS, secure cookies, and HSTS:** the current deployment intentionally uses local HTTP. Enabling these without a TLS reverse proxy would prevent login or make the local URL unusable.
- **SSO-only authentication:** requires an OAuth/OIDC or LDAP provider. Disabling password authentication now would lock out the administrator.
- **PostgreSQL or SQLCipher:** requires a planned migration and backup of the existing Open WebUI SQLite database.
- **Redis token revocation:** requires another persistent service. The current profile instead reduces token lifetime from four weeks to 24 hours.
- **Valve encryption:** the existing secret is not a Fernet-formatted key. Enabling it requires a key rotation, signs everyone out, and requires re-entry of encrypted valve values.
- **Disable plugins:** would remove the parsing, database, reader, and writer tools this project is built to use.
- **Disable code execution/interpreter:** removes in-chat code execution. It can be enabled as a hardening change after confirming that workflow is not needed.
- **Enforced CSP and cross-origin isolation:** can break model images, integrations, generated artifacts, and embedded content. CSP is currently report-only for validation.
- **Non-root/read-only Open WebUI container and stronger network segmentation:** require a custom image, writable-path inventory, and connectivity testing across Docker and Podman.
- **Offline mode:** may prevent embedding-model acquisition and document/RAG startup. It should be enabled only after required models are cached or when an air-gapped profile is requested.

## Reverse-proxy overrides

Before exposing Open WebUI through HTTPS, set at least:

```dotenv
OPEN_WEBUI_PUBLIC_URL=https://chat.example.com
OPEN_WEBUI_CORS_ALLOW_ORIGIN=https://chat.example.com
OPEN_WEBUI_FORWARDED_ALLOW_IPS=<reverse-proxy-address>
```

Then enable secure session/auth cookies and HSTS only after the HTTPS endpoint is working.
